Protocols · plain-language guide

MCP vs REST, in plain words.

You don't need the specs to understand the difference. You need one question: who decides which call happens — and when?

RESTA programmer decides. They read the docs, write the code, and the app makes exactly those calls, forever — decided before the app ever runs.
MCPAn AI model decides. It connects, asks "what can I do here?", and picks a tool to call — decided live, while it runs.

That's the whole difference. Everything on this page is just that one sentence, applied to something concrete.

Step 1

First, the two words

REST — how programs talk to programs

The standard way apps have talked to servers for ~20 years. Your app calls fixed web addresses — GET /orders/42 to read order 42, POST /orders to create one — and gets data back.

Key point: the app never improvises. Every call it makes was written by a programmer, ahead of time.

MCP — how AI models use tools

The Model Context Protocol (open standard, late 2024). You wrap your system in an "MCP server" that offers tools — actions like place_order or check_stock. Any AI app can connect, see the tools, and use them.

Think USB-C for AI: build the plug once, and Claude, ChatGPT, your IDE — every AI client — can use it. No custom integration per app.

Top: the dotted arrow — a person reading docs and writing code — happened once, before launch. Bottom: there is no dotted arrow. The model figures out what to call, every single time.

Why does that need a new protocol at all? Because before MCP, every AI app that wanted to use your system needed its own hand-built integration. 10 AI apps × 20 tools = 200 integrations. With one standard plug it's 10 + 20 = 30. That's the actual pitch of MCP — less glue code, not "REST is dead".

Figure 2

An MCP session is just a short conversation

Here is everything that happens when an AI agent uses an MCP server, written as the dialogue it really is. Two of the lines have official names — tools/list (asking what's available) and tools/call (using one) — and that's most of the protocol already.

diagram · one session, as a dialogue 
sequenceDiagram
    participant A as AI agent
    participant S as MCP server (your shop)
    A->>S: Hi — what can you do?  (tools/list)
    S-->>A: I have 3 tools: check_stock, place_order, track_order
    Note over A: User says: “order 2 chairs for me”
    A->>S: place_order(customer, 2 × chair)  (tools/call)
    S-->>A: Done — order no. 1042 created.
    Note over A: Agent reads the result and tells the user

Notice what the first two arrows replace: in REST, "what can you do?" was answered by documentation that a human read. Here the server answers it itself, live — so if you add a fourth tool tonight, every agent can use it tomorrow, with nothing redeployed on their side.

Under the hood the messages are JSON-RPC, carried over HTTP (for remote servers) or plain stdin/stdout (for local ones). Interesting if you're building a server; safe to ignore if you're just deciding between the two.

Step 4 · the subtle one

The description trick — the difference people miss

Here's the same "create an order" action, defined for REST and for MCP. They look almost identical. The difference is what the description text does — and this is the one non-obvious thing on this page, so it gets its own section.

REST · from the OpenAPI docs 
{
  "post": {
    "operationId": "createOrder",
    "summary": "Create an order",
    "requestBody": { "$ref": "NewOrder" },
    "responses": {
      "201": { "description": "Created" },
      "409": { "description": "Out of stock" }
    }
  }
}

Read by a human, once. If the summary is stale or vague, nothing breaks — the app was coded against the schema, and the schema is what matters.

MCP · tool definition 
{
  "name": "place_order",
  "description": "Place an order.
    Only call this AFTER the customer
    confirmed the cart. If an item is
    out of stock, the result names it —
    offer alternatives, don't retry.",
  "inputSchema": {
    "customer_id": "string",
    "items": "array"
  }
}

Read by the model, every time. The highlighted text is an instruction the model follows. Change it, and your system behaves differently — without any code change.

Three practical rules fall out of this:

Write descriptions like they're code

Because they are — they steer the model the way code steers a CPU. A vague description means the tool gets called at the wrong moment. Review description edits like you review code.

Write errors the model can act on

A REST app branches on 409. A model reads a sentence. "Out of stock: chair-oak-02 — suggest alternatives" gives it a useful next move. A bare 500 teaches it nothing, and it will just retry blindly.

Make tools match intentions, not tables

Code happily chains five small calls into one task. A model chaining five calls is five chances to pick wrong. So give it place_order — one tool, one intention — not POST /orders plus four lookups it must figure out.

Figure 3

They don't compete — they stack

This is the part headlines get wrong. In real systems MCP doesn't replace the REST API — it usually stands in front of it. You end up with two doors into the same backend: a REST door for programs, an MCP door for AI agents. Most MCP servers in production are thin adapters that call the same REST API you already had.

Your website keeps using REST — it doesn't need an AI in the middle. Agents come through the MCP door. Both end up at the same database, governed by the same rules.

One warning that matters even in the simple picture: the agent must act as the user, not as itself. If the MCP server calls your API with its own all-powerful service account, then every user of every agent silently gets those powers. Pass the real user's identity through, all the way down.

Decision

So which one should you use?

Program calling a program? → REST

Your frontend, service-to-service traffic, webhooks, cron jobs. No AI in the path means MCP buys you nothing there. Keep the types, keep the speed.

AI agent using your system? → MCP

Build one MCP server and every AI client can use it. Start with read-only tools (checking, searching); add write tools (ordering, deleting) later, with human approval in front of them.

Both kinds of caller? → Both doors

This is most real systems in 2026. REST for code, MCP for agents, same backend behind both — exactly Figure 3. It's an addition to your architecture, not a rewrite.

Still unsure? One test settles it: is anything in this call path deciding at runtime what to do next? No → REST. Yes → that part wants MCP.

Quick answers

The questions everyone asks

"Does MCP replace REST?"

No. It usually sits in front of it (Figure 3). What's true: for the AI-facing part of your system, MCP is becoming the standard door. Everything behind that door keeps working as before.

"Isn't MCP just another API?"

It is an API — that's fine to say. What's new is the caller: a model instead of code. That's why discovery is live, descriptions steer behavior, and errors are sentences. Same job, different reader.

"Can't the model just read my REST docs?"

It can, and it works — but every AI app did it its own way, which is the 200-integrations problem again. MCP's value is standardizing the plug, so one connector fits all clients. Boring on purpose.

"What's the catch with MCP?"

Nothing checks the order of calls anymore. In REST that order lives in reviewed, tested code; with MCP the model improvises it. The replacement is testing agent runs (evals) and guardrails before risky actions. If you can't invest in those yet, staying behind REST is a legitimate choice.
