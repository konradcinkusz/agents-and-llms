MCP vs REST: same domain, different consumer.

Every comparison of MCP and REST that starts from the wire format gets lost in the weeds, because the wire is the least interesting difference. Start from the consumer instead and the whole thing collapses into one sentence:

REST serves code that a developer wrote at design time. MCP serves a model that decides at runtime. Discovery, contract, errors, state, granularity — every real difference on this page is that sentence applied to a different column.

Figure 1

Two consumption paths to one domain

A REST integration is built before it runs. A developer reads the OpenAPI spec, writes client code against it, and from then on the running system executes exactly the calls that developer decided on — same endpoints, same order, every time. The intelligence is in the repo; the runtime just replays it.

An MCP integration is composed while it runs. The client connects, asks the server what it can do (tools/list), hands that catalogue to the model, and the model picks a tool and its arguments turn by turn. The intelligence is in the loop; nothing in any repo says which calls will happen, or in what order.

Same domain at the end of both rows. The dotted arrow is the whole difference: in REST it happens once, weeks before deployment, at a person's desk. In MCP its equivalent — discovery — happens in-band, on every session.

This is also why MCP exists at all. Before it, every AI application integrated every tool bespoke: N clients × M tools meant N×M adapters, each one a developer reading docs and writing glue. MCP standardises the client side of that loop — discovery, invocation, results-into-context — so a connector written once works in any MCP-aware client. N×M becomes N+M. That's a claim about integration economics, not about HTTP being obsolete.

Figure 2

On the wire

Mechanically: REST is HTTP verbs on resource URLs, strictly request–response, stateless by design. MCP is JSON-RPC 2.0 methods over one of two transports — stdio for local servers, streamable HTTP for remote ones — inside a session that starts with a capability handshake. And it is bidirectional: a server can ask the client's model to complete something (sampling) or ask the user a clarifying question (elicitation). A REST server can't ask its caller anything; it can only answer.

diagram · one MCP session 
sequenceDiagram
    participant M as Model
    participant C as MCP client (host app)
    participant S as MCP server
    C->>S: initialize — protocol version, capabilities
    S-->>C: capabilities — tools, resources, prompts
    C->>S: tools/list
    S-->>C: catalogue — names, descriptions, input schemas
    Note over M,C: user intent arrives, catalogue goes into context
    M->>C: call place_order(customer_id, items)
    C->>S: tools/call "place_order" {…}
    S-->>C: result — content for the model
    C->>M: result appended to context
    Note over M,S: loop — the model reads the result and may call again

The first four arrows are what REST doesn't have in-band. Their REST equivalent happened weeks earlier: a person read the docs and hard-coded the outcome. Here the catalogue arrives at runtime, so the server can grow a tool tonight and every connected agent can use it tomorrow, with no client redeployed.

One honest footnote on state: MCP started session-heavy and is moving the other way — the ecosystem push (stateless core, scaling on ordinary HTTP, OAuth-aligned authorisation) is making MCP servers deployable like any other web service. The Architecture page covers that trajectory; the short version is that MCP is converging on REST's operational virtues while keeping its own interface model. The differences that remain are the ones that can't converge, and they're all in the next section.

The real difference

The description is part of the interface

Put an OpenAPI operation next to an MCP tool and they look like the same thing wearing different clothes — a name, a schema, a description string. The difference is what the description string does.

REST · OpenAPI fragment 
{
  "paths": {
    "/orders": {
      "post": {
        "operationId": "createOrder",
        "summary": "Create an order",
        "requestBody": { "$ref": "#/…/NewOrder" },
        "responses": {
          "201": { "description": "Created" },
          "409": { "description": "Out of stock" }
        }
      }
    }
  }
}

Read by a human, once. If the summary goes stale, nothing breaks — the client code was written against the schema, and the schema is what CI diffs.

MCP · tool definition 
{
  "name": "place_order",
  "description": "Place an order for a customer.
    Only call this after the customer has
    confirmed the cart. If an item is out
    of stock, the result says which one —
    offer alternatives before retrying.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "customer_id": { "type": "string" },
      "items":       { "type": "array" }
    },
    "required": ["customer_id", "items"]
  }
}

Read by a model, every session. The highlighted prose is executed: it decides when the tool gets called and what happens on failure. Edit it and the system behaves differently — with no schema diff, no type error, no failing build.

Descriptions are load-bearing

In REST, documentation describes the interface. In MCP, documentation is the interface — the description is the only thing standing between the model and calling the tool at the wrong moment with the wrong intent. Tool descriptions are prompt engineering with a schema attached, and they deserve the same review discipline as code, because they change behaviour the way code does while diffing the way prose does.

Errors are read, not handled

A REST error is a status code for code to branch on — 409 means whatever the client developer decided it means, back at design time. An MCP tool error is text for a model to read and recover from. "Out of stock: SKU-1432; suggest alternatives" lets the agent take a sensible next step; a bare 500 teaches it nothing and invites a blind retry. In MCP, error messages are UX.

Granularity follows the consumer

REST grew resource-grained because code composes cheaply — a developer happily chains five endpoint calls into one use case. A model chaining five CRUD calls is five chances to pick wrongly, so MCP tools want to be intent-shaped: place_order, not POST /orders plus four lookups. This is the same rule the Architecture page derives for the migration: never wrap endpoints one-for-one.

The sequence is untyped

REST's compensating virtue, and it's a big one: the order of calls is in reviewed, tested client code. In MCP nothing types the sequence — the model may call tools in an order no one anticipated, and no contract artefact can fail a build over it. What replaces the type-check is evals over trajectories and guardrails before execution. If you can't afford that machinery yet, that's a genuine reason to stay behind REST.

Corrections

Four things people get wrong

"MCP replaces REST"

It sits in front of REST far more often than instead of it. The most common production MCP server is an adapter translating intent-shaped tool calls into the same REST endpoints that existed last year — Figure 3 below is the picture. The claim's honest core is narrower: for agent-facing integration surfaces, MCP is becoming the default doorway. The service behind the doorway keeps speaking whatever it spoke.

"It's just RPC with hype"

The wire is indeed unglamorous JSON-RPC. What's new isn't the encoding — it's who reads the contract. No prior RPC standard made natural-language descriptions a load-bearing part of the interface, defined a runtime discovery loop for a non-deterministic caller, or let the server ask its caller's model a question mid-request. Judge it by the loop it standardises, not by the framing bytes.

"OpenAPI already does this"

A model can read an OpenAPI spec and improvise calls — every lab demoed exactly that. What that leaves unstandardised is everything around the call: how the catalogue reaches the model, how results re-enter context, how auth is delegated, how the client and server negotiate what each supports. Each vendor solved that bespoke, which is the N×M problem again with extra steps. MCP's contribution is boring on purpose: one loop, agreed on by clients that compete.

"MCP is only tools"

Tools are one of three server primitives. Resources expose data for the host to place into context (the application decides, not the model); prompts are user-invoked templates. In the other direction, servers can request sampling and elicitation from the client. Reducing MCP to "function calling over the network" misses that it's a two-way protocol between a host application and a capability provider — the tool call is just its loudest message.

Figure 3

How they actually stack in production

The realistic end-state for a system that already has a REST API isn't a swap — it's two doorways into one domain. Deterministic consumers (your frontend, partner backends, cron jobs) keep the REST door: they benefit from typed contracts and don't need runtime discovery. Agent consumers get the MCP door, with tools shaped around intent. Both doors enforce the same identity and land on the same invariants.

The solid MCP→REST arrow is the pragmatic start: ship the MCP server as a facade. The dotted arrow is where you want to end up — both adapters as siblings on the domain. The trade-offs of facade-first, and the rule that keeps it survivable (intent-shaped tools from day one), are worked through in the middle state.

Two warnings that only apply to the stacked shape. Enforcement lives twice: the REST layer checks per endpoint, the MCP layer per capability, and wherever they disagree, the weaker one is your actual policy. Identity must be delegated: if the MCP server calls the REST API with its own service credentials, every user of every agent silently inherits the server's permissions — the tool boundary has to carry the user's identity all the way down.

Decision

Which one, when

Stay with REST when…

The caller is deterministic code: service-to-service traffic, your own frontend, webhooks, anything with hard latency budgets or contract-tested SLAs. No model in the path means MCP buys you nothing there — you'd be paying discovery and prose-contract costs for a caller that can't use either.

Reach for MCP when…

The caller is a model, or many different models: a capability that should be usable from Claude, an IDE, and an internal agent without three bespoke integrations. The wins are runtime discovery, one connector for N clients, and an interface a model can actually be steered by. Start with reads; gate writes behind approval from the first commit.

Run both when…

You have an existing API and agent consumers — which is most real systems now. Publish REST for code and MCP for agents, over the same domain and the same identity. Resist the one-for-one wrapper: tools are intent-shaped from day one or the agent welds itself to your old endpoint list.

The test that settles arguments

Ask one question about the consumer: is anything in this call path deciding at runtime what to call next? No — REST, and enjoy the types. Yes — that segment of the path wants MCP semantics: intent-shaped tools, readable errors, descriptions reviewed like code, and evals where the type-checker used to be.
